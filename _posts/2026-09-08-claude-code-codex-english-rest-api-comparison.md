기존 서비스에 영어를 추가하는 작업을 Claude Code와 Codex에 각각 맡겨봤습니다. 두 도구는 질문 방식, 위험 탐색과 완료 판단에서 차이를 보였습니다.

이번 사례에서 **Codex는 요구사항을 구현과 테스트로 연결하는 과정이 더 일관됐습니다. Claude Code는 설계와 검증의 허점, 실제 사용 상태를 더 깊이 확인했습니다.** 다만 이를 두 모델의 고정된 성격이나 성능 순위로 해석할 수는 없습니다.

| 도구 | 모델·추론 설정 | 작업 체계 |
|---|---|---|
| Claude Code | Opus 5 · xhigh | OMC 5.3.0 |
| Codex | GPT-5.6 Sol · medium | Superpowers 6.3.0 |

## 어떤 이슈를 설계하고 구현했을까요?

대상은 한국어·일본어·베트남어를 처리하던 REST API 서비스였습니다. 이름이나 연락처를 추출하는 NER와 개인정보 처리용 번역 기능에 영어를 추가하는 것이 공통 과제였습니다. 겉보기에는 지원 언어 목록에 영어를 넣는 작업이지만, 실제로는 입력 판정, 모델 실행, 번역, 화면 표시와 장애 대응까지 결정해야 했습니다.

| 설계 쟁점 | 결정해야 했던 내용 |
|---|---|
| 영어 모델 제공 | 기존 언어 처리에 영향을 주지 않으면서 영어 모델을 어떻게 제공할 것인가? |
| 자동 언어 판정 | 사용자가 언어를 지정하지 않았을 때 어떤 입력을 영어로 보낼 것인가? |
| 영어 번역 | 번역 엔진마다 지원 범위가 다를 때 영어 요청을 어떻게 처리할 것인가? |
| 사용자 화면 | 실제 서버와 화면의 지원 언어를 어떻게 일치시킬 것인가? |
| 장애와 완료 기준 | 영어 모델이 없을 때 어떻게 응답하고 기존 언어의 동작을 어디까지 검증할 것인가? |

이 서비스는 입력된 텍스트의 언어를 자동으로 판정합니다. 영어 지원에 판정 규칙 변경이 필요한 이유입니다. 하지만 라틴 문자가 있다고 영어인 것은 아닙니다. 프랑스어와 독일어도 라틴 문자를 쓰고, 짧은 이름과 혼합 언어 문장은 판정이 더 어렵습니다. 다른 언어로 분류되지 않은 입력을 영어로 보내려면 편의성과 오분류 위험 사이에서 선택해야 합니다.

번역 엔진마다 영어 지원 여부도 달랐습니다. 서버와 화면은 이 차이를 같은 기준으로 처리해야 합니다. 영어 모델이 없을 때 일부 기능의 실패가 서비스 전체에 미치는 영향도 확인할 필요가 있었습니다.

## 비교 전에 구분할 점

Codex에는 Superpowers 6.3.0이, Claude Code에는 OMC 5.3.0과 자체 하네스가 적용됐습니다. 하네스는 에이전트의 질문, 계획, 도구 실행과 검토 방식을 안내하는 작업 체계입니다.

두 세션은 같은 이슈에서 출발했지만 최종 요구사항은 달랐습니다. Claude Code는 더 넓은 라틴 문자 입력을 영어로 처리했고, Codex는 문자 범위를 제한했습니다. 영어를 지원할 번역 엔진, 검토 자원과 후속 요청도 같지 않았습니다.

그래서 기능 수나 테스트 통과 개수로 우열을 가리지 않았습니다. 사실 확인, 선택의 대가, 검토 의견의 검증과 전체 목적의 연결을 살펴봤습니다.

평가는 비공개 세션 로그, 구현 변경 내역, 테스트 및 배포 기록을 서로 대조해 작성했습니다. 기록이 없다고 행동도 없었다고 단정할 수는 없습니다. 동일 조건의 반복 실험과 시간·비용 측정도 하지 않았습니다. 아래 평가는 이 사례에서 관찰한 행동에 한정합니다.

## 요구사항 정의: 질문보다 중요한 전제

Claude Code는 모델 제공, 언어 판정, 번역과 화면까지 빠르게 짚었습니다. 주변 기능을 함께 살핀 점은 좋았습니다. 그러나 기존 동작이나 테스트 존재 여부를 잘못 이해한 채 질문과 설계를 진행하기도 했습니다. 사용자가 정정해야 전제가 바로잡혔고, 그만큼 교정 비용이 생겼습니다.

Codex는 기존 코드를 확인하고 요구사항을 테스트 가능한 조건으로 바꿨습니다. 허용할 입력과 실패 조건, 번역 엔진별 차이도 구체화했습니다. 다만 합의한 규칙으로 판단할 수 있는 예외까지 질문해 인터뷰가 길어졌습니다.

요구사항 정의는 Codex가 더 일관됐습니다. Claude Code에는 질문 전 사실 확인이, Codex에는 질문의 필요성을 가리는 판단이 필요했습니다.

## 의사 결정: 선택의 대가를 설명했을까요?

Claude Code는 라틴 문자를 영어로 보내면 다른 언어를 오분류할 수 있다고 설명했습니다. 그러나 잘못된 번역 예시 몇 개만 보고 사용자가 오류를 알아챌 것이라고 해석한 부분은 근거가 부족했습니다. 눈에 띄는 실패가 조용히 발생하는 오류까지 설명하지는 못합니다.

Codex는 요구사항 변경 전후의 결정을 추적하기 쉽게 기록했습니다. 다만 오분류 억제에서 더 넓은 기본 처리로 방향이 바뀐 일을 기존 결정의 구체화처럼 설명했습니다. 사용자가 승인했더라도 어떤 목표를 완화하거나 포기했는지는 밝혀야 합니다.

양쪽 모두 결정 기록은 충실했습니다. Claude Code는 관찰의 일반화를, Codex는 정책 변경을 완곡하게 설명하는 일을 경계해야 했습니다.

## 구현: 해결 장치의 크기를 통제했을까요?

Codex는 기존 구조로 요구사항과 구현을 연결했습니다. 번역 엔진별 지원 언어를 서버가 제공하고 화면이 이를 사용하게 해 중복 관리를 줄였습니다. 구현 순서가 실제 의존성과 충돌하자 계획을 조정했고, 실패하는 테스트와 최소 구현의 연결도 명확히 기록했습니다.

Claude Code도 핵심 기능을 구현했습니다. 그러나 문서에서 지원 언어가 빠지는 일을 막는 자동 검사가 점차 커졌습니다. 문서 수집 범위, 줄바꿈과 문장 형식까지 처리하다 검사 자체에 결함이 생겼습니다. 자동화가 실제 누락을 찾았더라도 유지할 규칙과 예외가 늘면 그 비용도 평가해야 합니다.

구현에서는 Codex가 변경 범위와 복잡성을 더 일관되게 통제했습니다. 다만 테스트 선행 기록만으로 일반적인 개발 역량을 단정할 수는 없습니다.

## 검토와 검증: 테스트가 통과해도 의심했을까요?

Claude Code는 검토 의견을 그대로 수용하지 않고 코드와 실행 결과로 대조했습니다. 기능을 일부러 망가뜨려도 검사가 통과하자 테스트가 보장하는 범위를 다시 살폈습니다. 영어 모델이 없는 환경에서 서비스 상태와 요청 실패가 어떻게 이어지는지도 확인했습니다.

이 발견에는 하위 에이전트의 기여도 있었습니다. 메인 에이전트는 발견을 검증하고 결과에 반영했습니다. 다만 자신이 만든 검사의 결함을 고친 일을 최초 구현의 장점으로 계산해서는 안 됩니다.

Codex는 요구사항별 테스트와 구현의 연결, 검증하지 못한 항목을 명확히 보고했습니다. 독립 검토가 찾은 누락도 수정했습니다. 다만 모의 객체를 이용한 장애 테스트와 실제 모델 로딩 실패를 재현하는 검증에는 차이가 있었습니다.

Codex는 변경 과정의 추적성이 좋았습니다. Claude Code는 테스트가 놓치는 오류와 실제 실패 조건을 더 깊게 확인했습니다.

## 완료 책임: 사용자가 실제로 쓸 수 있었을까요?

Claude Code는 실제 번역과 기존 언어의 동작을 확인하고 복구까지 준비했습니다. 실행 중 실수는 있었지만 최종 사용 환경을 확인한 증거는 충실했습니다.

Codex는 초기 검증에서 실제 번역을 확인하지 못했다고 보고했습니다. 당시 합의한 범위에서는 허용되는 제한이었습니다. 그러나 사용자 테스트 환경에서 번역 기능을 꺼둔 것은 별개였습니다. 사용자의 지적 뒤에야 전체 흐름을 연결했습니다.

개별 테스트 통과와 사용자가 전체 기능을 이용할 수 있는 상태는 다릅니다. 이번에는 Claude Code가 최종 사용 상태를 더 충실하게 확인했습니다.

## “Codex는 시키는 것만 잘하고, Claude Code는 알아서 하지만 과잉 설계한다”는 평가가 맞을까요?

일부 인상은 설명하지만 지나친 단순화입니다. Codex는 계획과 구현의 충돌을 해결하고 후속 조사에서 다른 오류도 찾았습니다. Claude Code는 주변 위험을 챙겼지만 사용자가 잘못된 전제를 고쳐야 할 때도 있었습니다. 많이 챙기는 것과 필요한 것을 정확히 챙기는 것은 다릅니다.

더 정확히 말하면 **Codex에서는 판단을 사용자에게 넘기는 비용이, Claude Code에서는 판단 범위를 스스로 넓히는 비용이 더 눈에 띄었습니다.** 실제 장애 재현이나 중요한 테스트의 허점까지 과잉 설계로 볼 수는 없습니다. 추가 검증이 줄이는 위험과 유지 비용을 함께 봐야 합니다.

## 하네스를 더 붙이면 해결될까요?

질문 방식, 설계 승인, 테스트 선행과 독립 검토 절차는 에이전트의 주의를 바꿉니다. OpenAI와 Anthropic의 공식 가이드도 질문, 검증과 하위 에이전트 사용을 지침으로 조정할 수 있다고 설명합니다.

그렇다고 부족한 행동마다 새 단계를 추가할 수는 없습니다. 독립 계획 검토, 테스트 판별력 검사와 요구사항 변경 감시를 항상 의무화하면 절차가 새로운 비용이 됩니다. 먼저 기존 단계의 책임부터 보완해야 합니다.

- 완료 검증에서는 대표 사용자 흐름과 실제 실행 설정을 함께 확인합니다.
- 코드와 승인된 요구로 답할 수 있는 가역적 선택은 에이전트가 직접 판단합니다.
- 요구사항이 바뀌면 이전 목표에서 무엇을 포기하거나 대체했는지 설명합니다.
- 독립 반박과 테스트 판별력 검사는 개인정보 처리나 장애 격리처럼 실패 비용이 큰 변경에 비례해 적용합니다.

번역 기능이 꺼진 환경은 기존 완료 확인만으로도 잡을 수 있었습니다. 반대로 한 기능의 실패가 다른 기능의 가용성에 영향을 준다면 독립 검토가 도움이 됩니다.

## 이 사례가 도구 선택에 주는 시사점

Codex를 사용할 때는 사용자에게 넘기는 판단이 많지 않은지, 완료 기준이 전체 사용 흐름까지 이어지는지 살펴봐야 합니다. Claude Code를 사용할 때는 초기 질문의 전제가 맞는지, 문제를 막는 장치가 문제보다 커지지 않는지 확인해야 합니다.

이는 한 사례에서 얻은 점검 기준입니다. 일반적인 우열을 판단하려면 같은 요구사항과 완료 기준으로 반복 비교해야 합니다. 질문과 결함 수뿐 아니라 사용자 교정 부담, 유지보수 비용과 실제 사용 가능성도 평가해야 합니다.
