Mike Hadlow의 [The Configuration Complexity Clock](https://mikehadlow.blogspot.com/2012/05/configuration-complexity-clock.html)(2012년 5월 7일)을 한국어로 요약했다. **값을 설정으로 옮기면 복잡성이 줄어들까**라는 질문을 던지는 글이다.

## 설정이 프로그래밍 언어가 되기까지

시계는 설정이 복잡해지는 단계를 나타낸다.

| 시각 | 변화 | 뒤따르는 비용 |
| --- | --- | --- |
| 12시 | 작은 프로그램의 값을 코드에 직접 작성한다. | 값만 바꿔도 다시 배포한다. |
| 2시 | 값을 설정 파일로 옮긴다. | 설정 항목을 관리한다. |
| 4∼5시 | 계층과 반복 구조를 가진 설정 모델로 확장한다. | 형식과 구조가 복잡해진다. |
| 6시 | 데이터베이스와 관리 화면을 갖춘 규칙 엔진을 도입한다. | 규칙을 표현할 전문 지식이 필요하다. |
| 9시 | 복잡한 조건을 표현하려고 DSL을 만든다. | 언어 구현과 유지 비용이 생긴다. |
| 다시 12시 | 자체 언어로 업무 규칙을 작성한다. | 버전 관리·회귀 테스트·배포가 다시 필요해진다. |

DSL은 업무 전용 언어다. 팀은 코어 수정 대신 도구가 부족한 자체 언어에서 개발하게 된다.

## 설정도 검증하고 배포해야 한다

설정이 업무 로직을 표현하기 시작하면 변경에 필요한 통제와 테스트도 늘어난다. 결국 설정 한 줄과 코드 한 줄의 변경 비용이 비슷해지고, 팀은 널리 쓰이는 언어 대신 자체 규칙 체계를 아는 사람에게 의존한다.

## 코드를 바꾸는 편이 단순할 수도 있다

저자는 일정 수준의 복잡성에서는 빠른 빌드·테스트·배포 체계를 갖추고 일반 프로그래밍 언어로 구현하는 편이 더 단순할 수 있다고 말한다. 규칙 엔진이나 DSL을 부정하는 주장은 아니다. 도입하기 전에 표현력뿐 아니라 구현·검증·학습 비용까지 따져 보라는 이야기다.
